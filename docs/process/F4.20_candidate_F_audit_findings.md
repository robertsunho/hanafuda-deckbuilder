## The governing design (the crux question, ANSWERED)

The locked F2.5 "Category 1 / Idea D" design (OVERHAUL_PLAN, locked 2026-05-15) is explicit:
a transcended (Negative) accumulator behaves as **"a fresh accumulator pre-seeded with the
transcend-moment output, accumulating linearly post-transcend at powerLevel-scaled rate."**

```
output = preTranscendTotal + (newEvents × scaling × powerLevel)
on each event (negative-side):  state.newEvents += 1
```

`incrementPerElement` fully implements the negative write-path: when `spirit.isNegative`, it
routes the increment to `newEvents` / `newEvents1` / `newEvents2` / `newT2Procs` by the spirit's
key markers. Every accumulator's `applyEngine` negative branch READS `preTranscendTotal +
newEvents × …`.

**Therefore: negatives are DESIGNED to keep accruing events post-transcendence.** Freezing a
negative at its snapshot (never feeding `newEvents`) is a HALF-COUNTING BUG — the read path
expects accrual the write path never delivers.

⇒ Of the original three: **Ants (allSpirits) is CORRECT. Ship & Moths (activeSpirits-only,
isNegative-guarded) are BUGGED.**

## Determination

**One category is implemented incorrectly** (Group 2 event-site increments that exclude
negatives), measured against the locked F2.5 design that says negatives accrue. It is NOT
"principled differences." Confirmed buggy: **engine_ship, engine_moths**. Likely more in the
unconfirmed rows. The fix direction is uniform: **Group-2 event-site increments must include
negatives** (iterate allSpirits / drop the isNegative guard), so `incrementPerElement` feeds
`newEvents` — exactly as Ants and Algae already do.

**Why it was easy to get wrong:** the scoring-loop path (Group 1) gets negative-inclusion FOR
FREE (the loop already iterates allSpirits), so those spirits are correct without anyone thinking
about it. The discrete-event sites (Group 2) each had to CHOOSE, and Ship/Moths chose
activeSpirits — plausibly by copying the `_fireSpiritHook`/`activeSpirits` pattern used for
non-accumulator hooks, where excluding negatives IS right. The bug is "applied the
non-accumulator iteration rule to an accumulator counter."

**Same bug class as:** Negative Osprey/Catcher reset bug, F2.4 item 10, F1.8.b followup #3.
This is the systematic root. Candidate C (naming `activeSpirits`/`allSpirits` by INTENT —
"scores" vs "accumulates-live-events") would prevent recurrence — the call-site choice is only
non-obvious because the getters are named by membership, not by which one accumulators need.
