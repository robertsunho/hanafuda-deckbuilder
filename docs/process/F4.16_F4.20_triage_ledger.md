# F4.16/F4.20 Triage Ledger — spirit-logic seepage bucketing

**Date:** 2026-06-04. **Author:** design conversation (Pass 2 over `F4.24_inventory_pass1.md`,
read against live source).
**Method:** Each site read in actual code, sorted by the three-part bucket-B test:
a site is **document-only (B)** ONLY if all three hold —
(1) it's a term in a formula a core system genuinely owns,
(2) lifting it would require inventing new indirection,
(3) the code reads clearer left in place.
Failing any one → **migrate (A)**. Default is A; B carries burden of proof.
A fourth bucket **(T)** = already owned by a separate scheduled task; not F4.16/F4.20 scope.

through the public RunManager API. They are the real F4.20 work. Precedent already exists:
`util_festival`, `econ_replica`, `econ_collector` are exactly this shape and already migrated.

### Site #6 — mirror/memory ctx-param — DEFERRED (recon gate did NOT pass)

The `spirits:` context array passed to every hook dispatch (currently `activeSpirits`) is consumed
ONLY by game_mirror (`_getMirrorTarget`) / engine_memory (`_getMemoryTarget`) for adjacency
targeting (SpiritEffects:185-206). Design intent: Negatives are valid targets AND targeters, so the
ctx should include them. The §5 recon gate before any swap:
- **(a) Does `allSpirits` order match the on-screen chain?** YES. The fan is built from
  `run.allSpirits`, and the drag handlers (`swapSpirits` RunManager:528, `moveSpirit` :541) mutate
  `_allSpirits` IN PLACE — so array order = placement order.
- **(b) Where does a Negative land on transcendence?** ❌ **APPENDED to the end of `_allSpirits`**
  (`_acquireSpiritStack` RunManager:784-786: `splice(idx,1)` then `push(...)`), NOT into the
  transcending spirit's slot. This contradicts the rule doc's "same placement in the chain" clause
  and is the named STOP condition ("transcend-append breaks adjacency").
- **(c) Index math** (`indexOf(self)` + left/right walk) would hold on a true-order array — but (b)
  means the post-transcendence position isn't where the regular was, so swapping the getter alone
  would silently change Mirror/Memory adjacency in a way tangled with the unresolved transcend-append
  question.

⇒ **Per the gate, site #6 was NOT edited** in F4.20-FIX2. **DECISION (Robert, 2026-06-06):**
transcendence must PRESERVE the spirit's chain position, not append to the end — appending is the
bug. Rationale: a transcended spirit can still be dragged/reordered like any spirit; there is no
reason for transcendence itself to relocate it, and relocating can surface unintended
anti-synergistic ordering mid-run. **Scoped follow-up = TRANSCEND-PLACEMENT FIX:** change
`_acquireSpiritStack` (RunManager ~:784-786) so the Negative replaces the transcending spirit
IN PLACE (preserve index) rather than `splice` + `push`-to-end. THEN the mirror/memory ctx swap
(this site #6) follows trivially — point the `spirits:` ctx at `allSpirits` (true placement order)
so Negatives are valid adjacency targets/targeters. Sequence: transcend-placement fix FIRST, then
the ctx swap + its tests. The deeper semantic question (do Mirror/Memory reference a slot vs
positional adjacency) remains a separate later task regardless.
