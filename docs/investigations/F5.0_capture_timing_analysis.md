# F5.0 Architecture Analysis — Capture-Timing Families + Vocabulary

**Type:** ANALYSIS (recon — zero behavior change). Produces evidence; **Robert rules**.
**Date:** 2026-06-23. **Phase:** 5A.
**Follows:** `F5.0_family_classification.md` (the 110-row table) and F5.0-FIX (Irrigation).
**Question:** is the **F2 vs F4** split (does an engine's increment count *this* capture's
score or the *next* one) **designed** or **incidental** — and what canonical vocabulary should
the families carry?

> **Bottom line (full argument in §3/§6):** for the only score-relevant spirits that exhibit it
> — **Wildlife & Plenty** — the non-self-counting (F4) behavior is **incidental**, not designed:
> it is the architecture's *one documented out-of-hook exception* ("those two spirits have no
> `onCardSeen`"), its gameplay impact is a marginal one-capture lag on a permanent accumulator,
> and no balance note anywhere relies on it. Their F2 sibling **Habitat** reacts to the *same
> event* (captured animals) and self-counts. **Recommend: consolidate** (move Wildlife/Plenty to
> `onCardSeen` self-counting, removing the exception), which lets "capture" mean one thing and
> spares the vocabulary a distinction players cannot feel.

## §1 — The increment-site map

For each score-relevant accumulator: where the count increments (**tally site**), where the
score-relevant value is read (**read site** — always `applyEngine`, Phase 2), whether the
**triggering capture's own card(s) count toward that capture's score** (self-counts?), and
**why the tally sits where it does** (designed = the engine's archetype needs that timing;
intrinsic = the triggering event genuinely happens there; incidental = an artifact of wiring).

Line cites are approximate (post-F5.0-FIX); hook/method names are the stable anchor.

## §2 — The F4 heterogeneity split (named explicitly)

F4 holds **two structurally different things**. The consolidation question is about the first
group only; the second has no "this capture vs next" axis because it does not score.

- **F4-scorers (the consolidation set):** `engine_wildlife`, `engine_plenty` — a score-relevant
  `applyEngine` read whose tally fires post-score in Region K. (`sym_algae` shares the post-score
  tally shape but is *intrinsic*, not incidental — §1b/§6.)
- **F4-reactions (NOT in scope):** `util_symbiosis`, `sym_caterpillar` (Region K roster/deck
  mutations), `util_glory` (`onCaptureComplete` draw), `util_festival` (stamp generation). These
  have **no score read at all** — they change roster/deck/hand/consumables. They cannot be "moved
  to F2 timing" because there is nothing to self-count. The consolidation must not sweep them in.

*(Mirror/Memory are DELEGATED — family inherited from the runtime target — and out of this axis.)*

## §3 — Consolidation cost / benefit (the core finding)

### 3a — Could the F4-scorers move to F2 timing without breaking?

**Yes, cheaply.** Wildlife/Plenty would gain an `onCardSeen` hook mirroring Radiance/Banner
(which already do round-reset *unique* tracking through `onCardSeen`):

```js
engine_wildlife: {
  onCardSeen({ card, spirit }) {
    if (card.type === 'animal') addUniqueToElements(spirit, 'seenAnimals', card.id);
  },
  applyEngine({ spirit }) { /* unchanged */ },
}
```

…and the two-line animal/plain branches in `RunManager.onCardsCaptured` (`RM:583-595`) are
removed. What it costs:

- **What moves:** ~10 lines from `RunManager.onCardsCaptured` → two `onCardSeen` hooks in
  `SpiritEffects`. This **removes the ARCHITECTURE-documented out-of-hook exception** (§2.2/§5:
  "the one place engine state is fed outside the hook system") — a net architecture *simplification*.
- **`ACCUMULATOR_SPIRIT_IDS` interaction:** both are already accumulators (the `seen*` arrays
  exist in `ACCUMULATOR_INIT`). `onCardSeen`'s per-card copy loop uses `count = 1` for
  accumulators and `addUniqueToElements` dedups — so firing once per card is correct, exactly as
  Radiance/Banner already behave. **No `ACCUMULATOR_SPIRIT_IDS` change needed.**
- **Tests that guard it:** the F5.0 recon already verified empirically (via the family table's
  §C-3) that Radiance self-counts and Wildlife does not; a move would flip Wildlife's behavior, so
  a 2-line "fresh unique animal boosts its own capture" test would pin it (mirroring the existing
  Radiance behavior). Low.
- **The negative path:** `NEGATIVE_SNAPSHOT` for wildlife/plenty (`snapshotArraysFromElements`)
  is unchanged — the transcend-boundary capture is identical; only the *seed* site moves.

### 3b — Is the self-counting difference **designed** or **incidental**?

**Incidental, for Wildlife/Plenty.** The weight of evidence:

- **Architecture frames it as a legacy exception, not a design.** ARCHITECTURE §2.2 and §5 call
  `onCardsCaptured`'s Wildlife/Plenty seeding "**the one documented exception — engine state fed
  outside the hook system**," with the stated reason "**those two spirits have no `onCardSeen`**."
  That is a *structural* reason (they lack the hook), not a *gameplay* reason (they should not
  self-count). It is documented as "intentional, not debt" only in the sense of *tolerated code
  structure*, never as a gameplay archetype.
- **No balance note relies on it.** Neither DECISIONS_LOG, V6, nor any balance pass states that
  Wildlife/Plenty *should* lag. (Contrast `D0.27`, where Ducks' timing *was* deliberately scoped
  and logged.) The recon's sweep found none either.
- **The gameplay impact is marginal.** Wildlife/Plenty are **permanent, run-scoped** accumulators
  ("+0.5 / +0.1 mult per unique … *forever*"). Not self-counting = a **one-capture lag** on a value
  that then persists for the whole run. Over ~36 rounds that lag is nearly invisible — it does not
  create a meaningful "sequencing" archetype.
- **The contrast proves the rule.** Radiance/Banner self-counting **is** load-bearing — they are
  **round-scoped** and reset every round, so a big bright/ribbon capture must compound *now* (×2
  per unique) or the engine barely fires. That is why they were (correctly) wired through
  `onCardSeen`. Wildlife/Plenty differ only in being permanent — and permanence is exactly what
  makes the timing not matter.

**So the split is clean, not tangled (the §4-premise check):** every F2 scorer self-counts
because that is either load-bearing (Radiance/Banner) or harmless-and-consistent (Devotion et al.);
the *only* non-self-counting score-relevant spirits are Wildlife/Plenty, and for them it is an
incidental artifact of the legacy seed site with marginal impact. There is no engine whose
*design* demands not-self-counting.

### 3c — The archetype framing (for Robert to weigh)

- **F2 self-counting rewards *concentration*** — assemble a big simultaneous capture, it all
  compounds at once.
- **F4 not-self-counting rewards *sequencing*** — build the counter, cash it on later captures.

The honest assessment: **the sequencing archetype is currently inert.** Its only vehicles
(Wildlife/Plenty) are permanent accumulators where the one-capture lag cannot be felt. A *real*
sequencing engine would need to be **round- or capture-scoped** (so the lag bites) — and no such
engine exists. So "keep-and-name" would canonize a strategic axis the game does not actually
express. If Robert *wants* a sequencing archetype, it should be built deliberately on a
round-scoped engine, not preserved as an accident of Wildlife's wiring.

## §4 — Vocabulary options (for Robert to rule)

Two axes are actually in play; the vocabulary should name the one that is load-bearing.

- **Axis 1 (real, load-bearing): per-card-re-runnable vs per-capture-once.** F1 (`onCardScored`)
  fires per card **and is re-run by the Phase-1.5 retrigger loop**; F2/F3 fire once per capture
  and are retrigger-immune. This distinction is load-bearing (Dew/Wish/Echo compound F1, never
  F2/F3) and deserves distinct words.
- **Axis 2 (the F2/F4 timing): self-count vs not.** Per §3, inert for the spirits that have it.

**Option A — Consolidate (recommended): `Scored` / `Captured` / `Reaction`** (+ live-read note).
- `Scored` = F1 (per-card, re-run by retrigger). `Captured` = F2 + F3 (once per capture,
  score-relevant; `Captured (live-read)` for the F3 run-state sub-variant). `Reaction` = F4
  (post-score, no score bearing). Requires moving Wildlife/Plenty to F2 self-counting (§3a) so
  "Captured" has **one** meaning.
- **Pro:** names only the load-bearing axis; every word honest; removes the architecture
  exception. **Con:** it is a behavior change (a marginal buff to Wildlife/Plenty) — needs a
  balance nod.

**Option B — Keep-and-name: `Scored` / `Seen` / `Captured` / live-read.**
- `Seen` = F2 (pre-score, self-counts); `Captured` = F4 (post-score). Preserves both behaviors.
- **Pro:** no behavior change. **Con:** canonizes Axis 2, which is **inert** for the only spirits
  that have it — players must learn a third capture-adjacent word for a distinction they cannot
  feel; and it leaves the architecture exception in place.

**Reach note:** under **B**, "Captured" (= F4 post-score) *matches* the capture-stamps, which
already say "When captured, +3 ki" for post-score reactions (§5) — so B is marginally more
consistent with *existing* stamp text. Under **A**, "Captured" means score-relevant; the stamps'
"captured" stays valid as a **trigger-moment** word ("triggers on capture") rather than a
scoring-family word — the two coexist at different levels, and the 2026-05-15 merge's "one atomic
capture event" framing already supports the umbrella use. This is the one place the two options
trade against the non-spirit seams; see §5.

## §5 — The non-spirit seams (consistency check — Robert flagged the reach)

### Capture-trigger stamps — **post-score, retrigger-compounded, say "captured"**
The yellow/orange/green/black/gray captured-stamps fire in the **post-score block of
`_scorePipeline`** (`GRM:1599-1613`) and **share the retrigger loop with F1** via
`_computeRetriggerCount(card, 'capture', …)`. Their data says `trigger: 'captured'` and their
text says "**When captured, gain +3 ki**" / "**Captured: draw +1**" (`consumables.js:187-255`).
So a stamp's "captured" = **a post-score reaction that triggers on capture and is
retrigger-compounded** — i.e. F4-timing, F1-retrigger-scope. One nuance: `stamp_white` ("When
captured, … scores twice") uses "captured" for a **scoring retrigger** (an F1 action), so even
within stamps "captured" already spans reaction *and* re-scoring.
- **Consistency verdict:** "captured" is *already* an umbrella trigger-moment word in the stamp
  layer (the 2026-05-15 merge unified `'scoring'`+`'capture'` into one `'capture'` trigger type
  precisely because they "fire in one atomic capture event"). **Option B** aligns "Captured"=F4
  with the stamps' post-score "captured" most directly. **Option A** keeps the stamps' "captured"
  as a trigger-moment word, distinct from the spirit scoring-family word — coherent, but it asks
  "captured" to do double duty. **No hard conflict either way**; flagged as the one trade.

### Wu Xing enhancements — **score-time effects vs event-time procs (separate axis)**
Enhancement *scoring* effects are **score-time, per-card**, applied in `_applyCardEnhancements`
(`GRM:1134-1155`, Phase 1, re-run by retrigger): Fire (+flat points), Water (×mult — its tooltip
even says "**×2 capture mult**", `consumables.js:79`), Wood (×mult), plus Metal/Earth held-in-hand.
These behave like **F1** ("Scored"). Separately, the **depreciation / break / proc events** (Snow→Ice,
Ember→Charcoal, Clay→Pottery, Wood-slot, Silk-anti-strand) fire at **round-end / event time**
(`_applyPostRoundEnhancements`, `GRM:655-740`) and *feed the F2 Wu-Xing engines*.
- **Consistency verdict:** the enhancement *scoring* effects map cleanly onto **"Scored"** under
  either option (no conflict). The depreciation/proc events are a **separate event-time axis** the
  capture vocabulary does not (and should not) describe — they want their own "proc/event" word, not
  "scored/captured". Water's "capture mult" wording is slightly loose (it is a score-time per-card
  mult that re-fires on retrigger), but it is an enhancement, **out of scope** for any spirit move —
  noted only so a future enhancement-vocabulary pass knows.

### F4.18 intersection
The deferred **F4.18** (capture-event dispatch consolidation — merging the Phase-1.5 scoring loop
and the post-score capture-stamp dispatcher, still two loops) is the **structural sibling** of this
question and carries Robert's own "revisit merged-vs-separated trigger types on playtest evidence"
note (DECISIONS_LOG, the 2026-05-15 patch). **It is independent in code** from the §3 recommendation:
moving Wildlife/Plenty's tally into `onCardSeen` touches `RunManager.onCardsCaptured` + `SpiritEffects`;
F4.18 touches `_scorePipeline`'s two loops. They are the same *theme* (capture-event timing) but
disjoint *edits*. If §3 is adopted, it can ship before, after, or independent of F4.18.

## §6 — Recommendation + dispositions

### Recommendation: **Consolidate (Option A)**, with a balance nod.
The F2/F4 timing split is **incidental** for the only score-relevant spirits that have it
(Wildlife/Plenty, §3b); consolidating their tally into `onCardSeen` is **cheap** (§3a), **removes
the architecture's one documented out-of-hook exception**, and lets "capture" carry a single
meaning so the vocabulary needs only the load-bearing **Scored / Captured / Reaction** axis (§4).
The only cost is a **marginal buff** (Wildlife/Plenty self-count) — a balance call, not a
correctness one. If Robert prefers to preserve a sequencing archetype, the honest path is to
**build it on a round-scoped engine** where the lag is felt, not to keep Wildlife's accidental wiring.

**Implied next campaign:** a **re-wire-then-rename** — (1) move Wildlife/Plenty to `onCardSeen`
self-counting (small `[FIX]`/balance edit + a self-count test), then (2) the cosmetic
vocabulary sweep (the F5.0 §A "captured"→"scored" rename targets) on the now-uniform families. If
Robert instead rules **Option B**, the next campaign is **rename-only** (no re-wire) — name F2
"Seen", F4-scorers "Captured", and leave the exception in place.

### Disposition of the three open recon items (analysis inputs — Robert rules)
- **Algae (§C-4): leave as-is.** Its post-score tally is **intrinsic** (summons happen in Region
  K), not incidental like Wildlife. It is a legitimate F2 scorer whose tally site is forced by when
  summons occur; it is **not** part of the consolidation. (Its description "each time a symbiont is
  summoned" is honest about the trigger.)
- **Festival (§C-2): F4-reaction on an F1 hook — recommend re-home, flag the interaction.** It
  generates stamps in `onCardScored` (returns null), so the side-effect is **re-run by the
  retrigger loop** (Dew/Wish/Echo multiply its stamp output) and fires per-ribbon-card. Recommend a
  future move to a reaction hook (`onCaptureComplete` / Region K) for consistency — **unless** the
  retrigger-compounding is a desired interaction (a real build-defining combo). That is a gameplay
  call for Robert; the analysis only surfaces it. Not in scope here.
- **Missing Number (§A borderline): confirmed F2, self-counts.** Tally `onStackCaptured` fires
  before its own Phase-2 read (`GRM:1514` < `:1516`), so a 4-stack capture boosts itself — genuine
  F2. Its description says "each time a 4-stack is **scored**"; under Option A's vocabulary that is a
  minor "scored"→"captured" rename candidate (low priority). No mechanical issue.
